# Loomit Vision

この文書は、Loomit が最終的にどこを目指すかを描く。出発点の動機は [`why.md`](why.md)、用語の定義は [`core-concepts.md`](core-concepts.md)、実装上の責務境界とデータモデルは [`architecture.md`](architecture.md) を参照。ここでは将来の到達像に絞る。

Loomit は、洋裁パーツを「作って終わり」にせず、履歴を残し、再利用し、組み合わせを検証できるローカル開発環境を目指す。
本格的な CAD は置き換えない。型紙作成や細かな幾何編集は Valentina などの外部 CAD に任せ、Loomit はその周辺の試作・記録・互換チェック・部品化・再利用を扱う。

## 目指すもの

Loomit が支援したいのは、次のような作業である。

- 市販型紙や既存型紙をもとに、少しずつ修正して試す
- 袖、襟、身頃、カフスなどを部品として保存する
- 気に入った部品だけを次の服にも使える資産として残す
- 一着ごとの組み合わせを明示し、あとから再現できるようにする
- 接続部の寸法や条件をチェックし、縫う前にズレを見つける
- 自分の体型や標準サイズに対して、着られるか、動けるかを事前に診断する
- 試作メモ、写真、失敗、改善案を履歴として残す

Loomit は、完成品だけを管理するアプリではない。作る途中の判断と変更履歴を残すための道具を目指す。

## 一着をプロジェクトとして扱う

Loomit は「一着」を1つのプロジェクトとして扱い、日常操作は CLI を中心にする。
互換チェックは lint や compile に近く、UI で毎回対象を選ぶのではなく、プロジェクトに書かれた組み合わせをコマンドで検証する。
プロジェクトの状態はテキストファイルとして残るため Git と相性がよく、差分を読んだり CI に組み込んだりできる。

（コマンドの詳細は [`cli.md`](cli.md)、ファイル形式と責務境界は [`architecture.md`](architecture.md) を参照。）

## 着られるか・動けるかを診断する

パーツ同士の互換だけでなく、「その服を着られるか（fit）」「その服で動けるか（movement test）」も、互換とは別の層として診断したい。

目指すのは、全テストに合格する服ではなく、服種別・用途・デザイン意図・布・過去の試作結果に応じて確認すべきリスクを選び、説明可能な形で検証した服である。
ユーザーに全テストを覚えさせず、`loom suggest-tests` が候補を提案し、採用・除外（理由付き）を決められるようにする。
物理シミュレーションから始めるのではなく、寸法とゆとり量にもとづくルールベース診断から育てる。

## 体型プロファイル

体型寸法を正確に測るのは難しいため、標準サイズ（`9A` など）からの選択・部分補正・自由入力を用意し、複数プロファイルを保存できるようにしたい。
体型（事実）と好み（preferences）は分けて持つ。
体型情報はセンシティブな個人データとして、ローカル保存を基本とし、共有や publish の対象にはしない。

## Loomit Studio（将来のUI）

GUI は Loomit 本体に密結合させず、`Loomit Studio` のような別ツールとして見据える。Studio はプロジェクトを直接いじるのではなく、Loomit core の API やコマンドを通して変更するため、CLI でできることと Studio でできることがズレにくい。

最終的には、画面上でギャザー範囲や縫わない辺、許容値を指定し、同じ互換エンジンで `loom check` を通し、なぜ通ったか・どの override が効いたかを説明できるようにしたい。重要なのは、Studio の操作結果もファイルに残ること。
UI だけの内部状態にはしない。

UI は必須の中心機能ではなく、プロジェクト作成・ライブラリ閲覧・エラーやグラフの可視化・プレビューなど、入口とデバッグ支援に寄せる。普段の作業は CLI で完結すべきである。

## パーツを資産として育てる

作業中のパーツを自動でライブラリに入れると、未完成・没案まで混ざってライブラリが汚れる。
再利用したいパーツだけを明示的に publish し、ローカルライブラリにコピーして資産化する。
元プロジェクトが壊れても資産が残るよう、参照し続けるのではなくコピーする。

（publish / library の具体フローとメタデータは [`architecture.md`](architecture.md) を参照。）

## 試作を、なくすのではなく整理する

Loomit は試作をなくす道具ではない。試作前に明らかなミスや高リスク箇所を減らし、確認すべき点を明確にする。
試作で得た知見（prototype notes）は、次回以降の test suggestion に活きる。

## 拡張できる形で始める

新しいパーツ種別・connector 種別・互換ルール・fit rule・movement test・importer・出力形式・外部UI などを後から足せるよう、互換チェックや build を CLI に直接書き込まず、Loomit core として分ける。CLI も Studio も同じ core を呼ぶ。

## 段階的に育てる

Loomit の価値は、最初から大きな統合アプリになることではない。
服作りの作業ディレクトリに自然に入り、`loom check` で安心できることから始める。
3Dシミュレーションや布物理、クラウド同期、マルチユーザーなどは後段に置く。
実装の順序と MVP の範囲は、内部の implementation plan で管理する。
