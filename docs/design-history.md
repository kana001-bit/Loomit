# Loomit Design History

この文書は、Loomit の設計がどのように育ってきたかを残すための初稿である。

ここで残したいのは、「最初から正しかった設計」の一覧ではない。どこで違和感が出たか、何を捨てて何を残したか、どういう問題にぶつかって今の形になったかを、後から読み返せるようにすることが目的である。

## Gitっぽく管理したいと思って始まった

Loomit の最初の発想には、最初から Git 的な感覚があった。

服作りでは、パターンを修正し続けるうちに、

- 今どのパターンが最新なのか
- どの案から派生したものなのか
- 前回から何を変えたのか
- 安心して前の案に戻れるか

が分からなくなりやすい。

最新だと思って布を切ったら、一つ前のパターンだったことがあった。
小さいパーツなら手持ちの生地でもう一つ切れるかもしれないが、大きいパーツだと生地を買いなおす必要がある。

Loomit は、試行錯誤そのものを管理しやすくするために考え始めた。

特に、既存の型紙や過去の服を少しずつ直しながら理想の形に近づける作り方では、「前回の案から何を変えたか」が分からなくなると次に進みにくい。

この時点ではまだ設計は粗かったが、Loomit を単なるファイル置き場ではなく、変更履歴を伴う服作りの作業環境にしたいという方向は早い段階からあった。

## git のつもりで始めたが、中身は validator に寄っていた

Loomit は最初から Git 的な道具として考えていたつもりだった。
ただ、実際に手を付けて形になっていった中身は validator 的な部分だった。

布を裁つ前に、

- 接続部の長さが合っているか
- 服の出来上がり寸法が成立しているか
- 動作テストの候補をどこまで機械的に拾えるか

を確認できれば、試作の手戻りを減らせる。

これは Loomit の出発点にあった切実な課題でもあった。
紙のパターンを直し、実寸で試作し、着てみて問題が出たらまた布を切り直す、というループはコストも大きく、精神的にも重い。

そのため、初期の Loomit は `check`、`fit`、`test`、`prototype-notes` のような「試作前に明らかなミスを減らす」方向から育っていった。

つまり、頭の中では Git を作ろうとしていたのに、実際に実装として先に現れたのは validator だった。

## そこで「思っていたものと違う」と気付いた

作りながら、途中で違和感が出てきた。
Loomit を validator としてだけ見ると、

- なぜ branch 的に案を試したいのか
- なぜ過去案との差分を読みたいのか
- なぜ prototype note を変更と結び付けたいのか
- なぜ「気に入った袖だけ次の服にも持っていく」という発想が強いのか

がうまく説明できなかった。

ここで見えたのは、Loomit が validator になってしまったというより、Git 的な道具として作り始めたのに、そのために必要な要素のうち validator 部分だけが先に育っていた、ということだった。

考え直してみると、やりたかったのは最初から「服の設計を Git のように試行錯誤すること」だった。

変更を試し、比較し、だめなら戻し、よければ採用する。validator はその流れを支える重要な部品ではあるが、中心そのものではなかった。

この認識が出てきたことで、Loomit は「validator から Git に方向転換した」というより、
「最初から Git を目指していたが、そのために足りない中心機能がまだ見えていなかった」と整理し直されることになった。

## 再利用の単位はパーツではなく、まず project だった

初期には、「前に作った腕を次のトップスにも使いたい」という発想から、再利用の単位がパーツ単体なのか project 全体なのかが曖昧だった。

検討を進めるうちに、まず必要なのはパーツ単体の参照共有ではなく、過去に作った一着全体を新しい出発点として複製することだと分かった。

つまり、

- だいたい似た服をもう一着作りたいときは project 全体を fork する
- fork 後は元 project と独立して進める

というモデルが自然だった。

これは実装都合だけではない。一度仕立てた服は、元の設計図を書き換えても勝手には変わらない。
過去の project は、その時点のスナップショットとして独立している方が、服の物理的な感覚にも合っていた。

## そのあとで、パーツ単位の library が別に必要だと分かった

一方で、「この袖だけ気に入ったから別の服にも使いたい」という要求は確かにあった。
ここで見えてきたのは、project の fork とパーツの再利用は似ているようで別の動機だということだった。

- project の fork は、一着全体の文脈ごと持っていく操作
- library は、気に入った部品だけを資産として抜き出す操作

この役割分担が見えてから、library は「参照し続ける共有部品」ではなく、「コピーして使い、コピー先で自由に直す」モデルに寄った。これは shadcn/ui 的な扱いに近い。

この時点で、Loomit は「project を複製して育てる流れ」と「part を publish して流用する流れ」を分けて考えるようになった。

## version ではなく name + variant に考え直した

次に大きかったのは、パーツの `version` という考え方が服作りに合っていないと気付いたことだった。

ソフトウェアでは、新しい version が古い version より進んでいる、という前提を置きやすい。
しかし洋裁パーツでは、`puff-sleeve-v3` と `puff-sleeve-v5` は優劣のある新旧ではなく、単に違う選択肢であることが多い。

この違いが見えてから、

- `name` と `variant` を分ける
- `variant` を大小比較しない
- 互換判定は version 比較ではなく寸法条件で行う

という方向に設計を修正した。

これは細かいスキーマ調整ではなく、Loomit が何を比較し、何を「新しいもの」と見なさないかを決め直す重要な転換だった。

## prototype notes は project state とは別物だった

試作を繰り返していると、残したいのは現在の寸法や connector 情報だけではなかった。

「この条件では腕が上がりにくかった」「この形だとまだ突っ張る」「この残布なら襟やカフスに再利用できる」といった知見は、服そのものの状態ではなく、作る人の経験だった。

そのため、`prototype-notes` は `loomit.yml` の中に埋め込むより、独立した知識データとして扱う方が自然だった。

また、project を fork して服の実体は分岐しても、試作から得た学びは引き継がれてよい。
ここでも「服の状態」と「作る人の知識」は別だという整理が効いた。

## Git 的に扱いたいのに diff が足りなかった

ここで、設計の中心的な欠落がはっきりした。

project を fork できても、library を持てても、prototype note を残せても、変更を意味のある差分として読めなければ Git 的な作業は成立しない。

当時の Loomit では、変更はまだ ファイル内容（blob）の差分 に近く、
「ダーツ幅を変えた」「ダーツを移動した」といった設計上の変更が、バージョン管理に使える形で見えていなかった。

ここで初めて、「足りなかったのは diff だ」と明確に言えるようになった。

Loomit の中心を validator だけで考えていた時期には、この欠落は見えにくかった。
Git 的な道具として見直したことで、diff の必要性が前景化した。

## diff 可能なドメインにしないとバージョン管理にならない

diff が必要だと分かると、次の問題はもっと根本的だった。

単に `loom diff` というコマンドを生やせば解決するわけではない。比較されるデータ自体が diff 可能な構造になっていなければ、出てくるのは座標やファイルの差分でしかない。

特に大きかったのは、ダーツのような「人がよく触る編集フィーチャ」が schema に十分現れていなかったことだった。

ダーツ幅を 30mm から 35mm に変えたことを、

- 座標の塊の変化として見るのか
- 編集フィーチャのパラメータ変更として見るのか

で、意味のある履歴になるかどうかが大きく変わる。

ここで設計は、「座標を比較する」のではなく、「編集フィーチャを id 付きの構造として持ち上げ、その差分を読む」方向に進んだ。

## `.val` と `part.loom` の役割分担がはっきりした

diff を成立させるために、幾何の正本と Loomit 側の表現の境界も見直された。

Valentina の `.val` は、座標の塊ではなく、点や数式や寸法参照を持つパラメトリックな構築レシピである。
そこには設計変更の粒度を持ち込める余地がある。

一方、Loomit が自前で CAD の write を持ち始めると、責務が急に重くなる。

そのため、

- 幾何の正本は `.val`
- `part.loom` は `.val` から射影した domain representation と Loomit 固有メタ
- Loomit は read と解析と diff を担う
- geometry の focused check は Seamlint
- 実際の補正や CAD write は Truer あるいは外部 CAD 側

という線引きが整理されていった。

この時点で、`loom diff` は Loomit から外すべき機能ではなく、
むしろ Loomit が正本ファイルの意味を読むための中核機能として位置付いた。

## diff は比較表示ではなく design review surface になった

diff を入れるだけなら、単なる比較表示で終わる可能性もあった。

しかし実際には、Loomit が必要としていたのは「この変更案を残すか、捨てるか」を判断するための読み面だった。

そこから、

- decision summary
- prototype note との関連付け
- Seamlint へ渡す re-check hints

のような方向が見えてきた。

つまり `loom diff` は、ファイル差分を見る画面ではなく、設計判断のための surface になっていった。

## 自己シームが表せない！

`loom add` に connector(縫い合わせ先 = join)を対話で複数登録できるようにしたあと、別の不足に気づいた。

一つのパーツには縫い目が複数ある。袖なら、アームホール、袖口、そして袖をわっかにするための袖下の縫い目。
最初の二つは別のパーツ(身頃・カフス)と縫い合わせる join だが、袖下は**同じパーツの二辺を縫い合わせる自己シーム**で、相手のパーツがいない。

connector は「二つのパーツが同じ id を宣言したらペア」で接続を表す。
だから相手のいない自己シームは、この仕組みに居場所がなかった。
複数登録はできるのに、どれが自己シームで、どことどこを縫うのかを表せない。

...ユーザーに入力させる？やっぱりインターフェースが必要じゃないか！

これを表すには connector を「seam(長さや滑らかさを持つ辺)」と「join(辺どうしの関係)」に割る抽象が要るのだと思い、設計が急に重くなる予感がした。

しかし、自己シームで確認したいことを並べてみると、

- 前後の辺の長さが揃っているか
- 閉じ目で線が滑らかに繋がるか
- ちゃんとわっかに閉じているか

これらは全て**幾何の測定**であり、Loomit は幾何を計算しないと決めた方針(A案)の外だった。測るのは Seamlint の仕事である。

そして Seamlint の geometry check request を見ると、check の `from` と `to` は**同じパーツを指してよい**。
つまり自己シームは「同一パーツの二つの path を比べる check request」として、**新しい抽象なしで**表せる。
滑らかさは `smooth-continuation`、長さは `sewn-seam`、わっか閉じは `closed-loop`。
恐れていたインターフェースは要らなかった。

ここで connectivity の定義を締めた。

- **connector は、複数のパーツを組み合わせる cross-part join 専用**とする。
- **自己シームは Loomit のモデル要素ではなく、Seamlint への check request**として扱う。

### そうしたら、check が何をする子か分からなくなった

自己シームを Seamlint に預けた途端、逆に `loom check` の輪郭が分からなくなった。幾何の検査は Seamlint へ、`.val` の射影を読むのは diff へ寄っていて、気づけば check の「中身」は両側から削られていた。
check は元々 validator として生まれた機能で、その validator 時代の遺物が残っていたのだ。

そこで、幾何を持たない今の Loomit が check で何を確かめられるのかを引き直し、三つの役割に整理した。

1. **Well-formedness(構造)**: `loomit.yml` と全 `part.loom` が parse でき、schema に合い、role と type が一致し、参照が解決する。Loomit にしかできない、一番固い芯。
2. **assembly グラフの整合(宣言ベース)**: connector グラフが筋が通っているか — mate が両側に宣言されているか、宙ぶらりんや誤ペアの join がないか、requirement が満たせるか。幾何ではなく garment graph の話なので Loomit ネイティブ。最初に心配した「自己シーム / open-join の取り違え」はここに住む。
3. **Seamlint への受け渡し**: グラフから導かれる幾何チェック(`sewn-seam` / `smooth-continuation` / `closed-loop`)の request を発行するだけ。check は「幾何的に何が真であるべきか」を言い、Seamlint が「実際そうか」を測る。

### 責務境界が落ち着いた

この整理で、Loomit・Seamlint・Truer の分担がはっきりした。

- **Loomit**: 構造とグラフ(宣言レイヤ)。`part.loom` / `loomit.yml` が valid で、assembly として矛盾がないかを見る。
- **Seamlint**: 幾何の測定。長さ・滑らかさ・閉じを SVG から測って verdict を出す。
- **Truer**: Seamlint が見つけた問題を、人が承認したぶんだけ直す。

これに伴い、check の `connector-length` の位置づけも定まった。
あれは幾何を測っているのではなく、**宣言済みの `length_mm` 同士の sanity**(「469 と 470、許容内」程度)であり、長さの本当の verdict は Seamlint が持つ。宣言値は実 SVG に対して古くなりうるので、declared-sanity として軽く残す(SVG 不要)か、Seamlint への request に畳むかは、まだ選べる余地として残している。

始まりは「自己シームが表せない」という小さな不足だったが、辿ってみると connector の意味・check の役割・Seamlint との境界を、もう一度引き直す作業になっていた。

## SVG では情報が足りない...

Seamlint と連携することを考え始めた当初は、geometry の受け渡しには SVG を使うつもりだった。
SVG は描画結果そのものなので、幾何を測るだけなら十分だろうと考えていた。
しかし実際に Valentina の export を調べてみると、Loomit が必要としていた情報が思った以上に失われていた。
特に困ったのは、以下の点。

- `detail` の identity (`details_name` や `details_id`)
- notch の情報
- 「どの geometry がどのパーツなのか」を結び付けるための手掛かり

描画結果としては正しくても、Loomit が意味を持って扱いたい情報までは残っていない。
「SVG を唯一の受け渡し形式にする」という前提は、この時点で崩れた。

### Valentina に pull request を出す？

最初に思い浮かんだのは「Valentina に足せばいいのではないか」ということだった。
Valentina は OSS なので、自分で修正して pull request を出せる。
実際に develop ブランチや issue を調べ始めたところ、別の事実が見えてきた。

洋裁 CAD の世界には、SVG とは別に DXF(AAMA / ASTM) という受け渡し形式があり、そちらには geometry と identity を結び付けるための情報が最初から含まれていた。
自分が CAD の世界に既にある受け渡し形式を知らずに、デフォルトの出力形式にあった SVG を安直に選んでいただけだった。

## SVG ではなく DXF(ASTM) にたどり着いた

そこで Valentina が出力できる DXF(AAMA / ASTM) を実際に調べた。
確認してみると、DXF(ASTM) には geometry だけでなく、`detail` の identity と結び付けられる情報も保持されていた。
つまり、

- `.val` は設計意図や意味を持つ正本
- DXF(ASTM) は geometry の受け渡し
- Loomit は両者を対応付ける橋渡し
- Seamlint は geometry を測定する

という責務分担が自然に成立することが分かった。
ここで、SVG は「表示用 artifact」として扱い、geometry handoff は DXF(ASTM) を使うという方向が固まった。

## geometry handoff が先に固まった

本来、Loomit の中心として考えていたのは diff や snapshot のような Git 的な体験だった。
しかし、Seamlint と接続するには「何を渡すのか」という境界を先に決めなければならなかった。
geometry の責務が曖昧なままでは、diff を作っても、check を作っても、どこまでを Loomit が担当するのかが定まらない。
結果として、Git 的な中心機能よりも先に geometry handoff の設計を固めることになった。

## diff だけでは足りない — snapshot を誰が持つか

diff が読めるようになって、もう一段深い欠落に気づいた。

`loom diff` は「2つある状態を比べる」道具だが、**変更前の状態そのものを残す仕組みではない**。同じ `part.loom` や `.val` をその場で上書きすれば、比較元は消えて diff は取れない。fork はディレクトリの複製であって、内部の history ではない。

つまり「変更を覚えておいて後で差分を読みたい」という要求は、実は「**前の snapshot を残しておきたい**」という要求だった。branch には枝分かれ元の過去状態が要るし、commit には「この時点の project state」を固定する単位が要る。diff はその後で、2つの snapshot を比べて初めて読める。

ここで分岐は2つあった。

- **A. history は Git に委譲する** — 変更前の保持・branch・commit・merge は Git が担い、Loomit は2つの commit / worktree / project を domain diff で読む。
- **B. Loomit 自身が snapshot / revision を持つ** — `loom snapshot` のような操作で state を保存し、Loomit 内で changes / revision / branch を扱う。

迷ったが、A を基本にすると決めた。

理由は、Loomit の正本がすでにテキストファイル（`loomit.yml` / `part.loom`）だから。「files が正本」という方針は Git と素直に噛み合い、「同じ名前の `.loom` を上書きしても前の状態が残る」は Git の commit で自然に満たせる。B を選ぶと、snapshot 保存形式・親参照・branch pointer・GC・merge の責務まで設計が広がり、Git と二重の history を抱える。それは「files が正本」「CAD write は外部委譲」という今の方針と対立する。

大事だったのは、**Loomit が再実装すべきなのは version control ではない**という線引きだ。branch engine を自前で持つより先に要るのは、「diff は snapshot 間の比較である」と整理を明示し、Loomit は洋裁の意味論（意味的 diff・互換・再利用）に集中することだった。history storage は枯れた Git に預ける。

そのため、Loomit 単体で `commit` / `branch` を持つところまでは、あえて設計を閉じていない。次に自然なのは自前の revision store ではなく、`loom diff` を Git の2 revision と結びつけて呼べるようにする方向だと考えていた。

### そして「revision と結びつけて呼ぶ」は実装された

その次の一歩は、想像していたより素直に踏めた。files が正本で、各 snapshot が Git の commit として既にそこにあるなら、Loomit がすることは「その版のファイルを一時 worktree に展開して、いつもの意味差分に流す」だけでよかった。自前の revision store も、snapshot 保存形式も要らない。`loom diff main..HEAD --part body` は2つの snapshot を比べ、`loom diff <rev> --part body` はその snapshot と作業ツリー（未コミットの変更）を比べる。git shell は CLI 層に閉じ、core の diff は pure なまま保った。

ここで用語も固定した。leaning A の下では、区別すべきは2語で足りる。

- **snapshot** = ある時点の Project state そのもの（概念）。`loom diff` が比較する状態。
- **revision** = その snapshot を addressing する **Git の revision**（`main` / `HEAD` / SHA）。1つの版＝1つの snapshot で、`loom diff <rev>` が受け取る handle。`main..HEAD` はこの revision を2つ並べた**範囲**（＝2 snapshot の比較）で、revision そのものではない。

**commit** は Git の動詞のまま残し、`loom commit` / `loom snapshot` という Loomit 独自の保存 verb は作らない。snapshot を作る・履歴を持つのは Git の仕事で、Loomit は snapshot を**読む**（意味的 diff）ことに集中する。この「Loomit は独自の revision surface を持たない」は、Studio を作るときに UI の一貫性のために revision を見せたくなったら再検討する余地として残すが、CLI/core の v0 では持たない。定義は [glossary.md](glossary.md) の Snapshot / Revision を正とする。

## 「1本の縫い目 = 2枚」が崩れた — assembly は tree だった

自己シームを整理したとき、connector は「複数のパーツを組む cross-part join 専用」と定めた。そして check の役割②(assembly グラフの整合)は「join id を宣言するパーツがちょうど2枚か」で健全性を見ていた。1枚なら相手待ち(warning)、3枚以上なら over-pair(error)。

実際の `waist.val`(前・後ろ・脇・袖…の7ピース)を add したとき、この over-pair が `side` や `armhole` で発火した。最初は「正しく捕まえた」と思った。実際、当時の `loom add` は id を使い回して同名 join を量産していたので、これはバグ検出として機能していた。

だが、set-in sleeve の armhole を思い浮かべると、前提そのものが崩れた。**armhole は「1本の縫い目 = 2枚」では表せない、ごく普通のデザインだった。** 身頃側の armscye は front + side + back の armhole 辺が**端でつながって1本の連続カーブ**になったもの。袖側の袖山は upper + lower が連続したもの。armhole はこの「多パーツの端 ↔ 多パーツの端」を1本で縫う。無理に `front-armhole ↔ upper-sleeve` のような piece-pair に割ると、**存在しない縫い目を捏造する**ことになる。

### 「2枚じゃない」には2種類あった

「2枚とは限らない」を掘ると、別々の現象が混ざっていた。

- **連続した複合エッジ(contiguous)** — armscye のように、複数ピースの辺が端でつながって1本の長い辺になり、反対側(袖山)と**各側の和で**合う。辺のレベルでは2側だが、各側が多ピース。
- **重なった同一エッジ(coincident)** — 見返し・裏地・玉縁のように、**同じ長さの N 枚を重ねて1本で縫う**。これは本当に N-ary で、全部同じ長さ。

そして「ポケットは3枚?4枚?」と数え始めて、迷子になった。前身頃＋ポケット後ろ側＋蓋なのか、分かれるのか…。だが、その迷いこそが答えだった。**ポケットは「1本の縫い目」ではなく、複数の縫い目の束**(脇の上・脇の下・袋の周り・開口部)で、縫い目ごとに割れば参加者は毎回はっきりする。構成は服ごとに変わる。だから **モデルは「ポケット」を知らなくていい** — 作者が各縫い目の参加者を宣言し、Loomit は健全性だけを見ればいい、と決まった。

### 決定 — seam は「参加エッジの集合」、over-pair は退役

connector(seam)を、**作者が宣言する参加エッジの集合**として捉え直す。各参加は **coincident(重ね・N枚等長)** か **contiguous side(連続側・和が一致・側はちょうど2)** のどちらか。「3枚以上 = error」の over-pair は**退役**させた。あれは主に `loom add` の id 使い回しバグを捕まえるためのもので、それは add 側の identity を直した(種類 type と一意 id を分けて訊く)ことで根を断ったからだ。id を使い回さなくなれば、N 枚が1本の縫い目に参加するのは正当なデザインとして通してよい。もし宣言だけ N-ary で幾何的に破綻していれば(等長でない5枚など)、それは**長さの実測**で分かる話で、そこは Seamlint が担う。N-ary や和のジオメトリの測定は Seamlint に defer した — Loomit は宣言、Seamlint は幾何、という分担のまま。

### 「組み立て可能か」は誰も一人では言えない

ここで「本当に組み立てられるか(全部の辺が縫われるか / 余った辺は無いか)」を Loomit で言えないか、と考えた。だがすぐに壁に当たった。Loomit が持っているのは **part ↔ part のグラフ**(どの join id を誰と誰が宣言したか)だけで、**どの物理辺を縫うか**は持っていない(connector は辺に束縛されていない)。「余った辺を探して閉じるか」は**エッジレベル**の話で、辺を持つ Seamlint なら(各ピースの辺を列挙し、どの辺が seam に消費されたか特定して)余りを出せる。ただし「余った辺がデザイン上の自由端(裾・衿ぐり・あき)か、縫い忘れか」は作者の宣言が要る。つまり完全な組み立て可能性は **Loomit(グラフ)＋ Seamlint(辺)＋作者(自由端の宣言)** の協業で、誰か一人では言えない。これは大きいので将来に置いた。

一方で、**グラフだけで言えること**はある。作者が「{front, side, back} を身頃側(unit)」と宣言したなら、「その3枚が他の縫い目で本当に互いに繋がっているか」は、辺を知らなくてもグラフの到達性で確かめられる。繋がっていなければ「unit と宣言したのに繋ぐ縫い目が無い」と warning で促す — ブロックはしない(seam を端折れる `loom add` の未完を罰しないよう、作者が unit と宣言した側にだけスコープする)。

始まりは「7ピースを add したら over-pair で怒られた」だったが、辿ってみると assembly グラフは flat な多重グラフではなく、**二分の join を積み上げる tree/DAG** だった、という認識の引き直しになった。Loomit は「誰が・どう組むか」の構造とグラフ整合を持ち、「その縫い目が幾何的に合うか(和・いせ)」の測定は Seamlint、「どの辺が自由端か」は作者 — という責務が、ここでも同じ形で現れた。

## まだ途中にあるもの

今の Loomit は、最初の発想だった「洋裁の git」に完全に到達したわけではない。

まだ途中にある課題も多い。

- どの編集フィーチャまで `part.loom` に持ち上げるか
- diff の粒度をどこまで human-readable にするか
- prototype note の関連度をどう絞るか
- Seamlint と Truer の境界をどう保つか
- `connector-length` を宣言メタの sanity として残すか、Seamlint への check request に畳むか

（`loom diff` を Git の revision とどう結びつけて呼ぶかは、上の「そして『revision と結びつけて呼ぶ』は実装された」で決着した — snapshot=概念 / revision=Git handle、独自 revision surface は持たない。）

ただ、少なくとも今は、何が不足していて、なぜその不足が問題なのかを以前よりはっきり言えるようになった。

その意味で、この設計史は「完成した正解」の記録ではなく、Loomit が validator から git 的な道具へ考え直され、そのために diff 可能なドメインを必要とした過程の記録である。
