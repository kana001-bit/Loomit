# Loomit Design History

この文書は、Loomit の設計がどのように育ってきたかを残すための初稿である。

ここで残したいのは、「最初から正しかった設計」の一覧ではない。どこで違和感が出たか、何を捨てて何を残したか、どういう問題にぶつかって今の形になったかを、後から読み返せるようにすることが目的である。

## Gitっぽく管理したいと思って始まった

Loomit の最初の発想には、最初から Git 的な感覚があった。

服作りでは、パターンを修正し続けるうちに、

- 今どのパターンが最新なのか
- どの案から派生したものなのか
- 前回から何を変えたのか
- 安心して前の案に戻れるか

が分からなくなりやすい。

最新だと思って布を切ったら、一つ前のパターンだったことがあった。
小さいパーツなら手持ちの生地でもう一つ切れるかもしれないが、大きいパーツだと生地を買いなおす必要がある。

Loomit は、試行錯誤そのものを管理しやすくするために考え始めた。

特に、既存の型紙や過去の服を少しずつ直しながら理想の形に近づける作り方では、「前回の案から何を変えたか」が分からなくなると次に進みにくい。

この時点ではまだ設計は粗かったが、Loomit を単なるファイル置き場ではなく、変更履歴を伴う服作りの作業環境にしたいという方向は早い段階からあった。

## git のつもりで始めたが、中身は validator に寄っていた

Loomit は最初から Git 的な道具として考えていたつもりだった。
ただ、実際に手を付けて形になっていった中身は validator 的な部分だった。

布を裁つ前に、

- 接続部の長さが合っているか
- 服の出来上がり寸法が成立しているか
- 動作テストの候補をどこまで機械的に拾えるか

を確認できれば、試作の手戻りを減らせる。

これは Loomit の出発点にあった切実な課題でもあった。
紙のパターンを直し、実寸で試作し、着てみて問題が出たらまた布を切り直す、というループはコストも大きく、精神的にも重い。

そのため、初期の Loomit は `check`、`fit`、`test`、`prototype-notes` のような「試作前に明らかなミスを減らす」方向から育っていった。

つまり、頭の中では Git を作ろうとしていたのに、実際に実装として先に現れたのは validator だった。

## そこで「思っていたものと違う」と気付いた

作りながら、途中で違和感が出てきた。
Loomit を validator としてだけ見ると、

- なぜ branch 的に案を試したいのか
- なぜ過去案との差分を読みたいのか
- なぜ prototype note を変更と結び付けたいのか
- なぜ「気に入った袖だけ次の服にも持っていく」という発想が強いのか

がうまく説明できなかった。

ここで見えたのは、Loomit が validator になってしまったというより、Git 的な道具として作り始めたのに、そのために必要な要素のうち validator 部分だけが先に育っていた、ということだった。

考え直してみると、やりたかったのは最初から「服の設計を Git のように試行錯誤すること」だった。

変更を試し、比較し、だめなら戻し、よければ採用する。validator はその流れを支える重要な部品ではあるが、中心そのものではなかった。

この認識が出てきたことで、Loomit は「validator から Git に方向転換した」というより、
「最初から Git を目指していたが、そのために足りない中心機能がまだ見えていなかった」と整理し直されることになった。

## 再利用の単位はパーツではなく、まず project だった

初期には、「前に作った腕を次のトップスにも使いたい」という発想から、再利用の単位がパーツ単体なのか project 全体なのかが曖昧だった。

検討を進めるうちに、まず必要なのはパーツ単体の参照共有ではなく、過去に作った一着全体を新しい出発点として複製することだと分かった。

つまり、

- だいたい似た服をもう一着作りたいときは project 全体を fork する
- fork 後は元 project と独立して進める

というモデルが自然だった。

これは実装都合だけではない。一度仕立てた服は、元の設計図を書き換えても勝手には変わらない。
過去の project は、その時点のスナップショットとして独立している方が、服の物理的な感覚にも合っていた。

## そのあとで、パーツ単位の library が別に必要だと分かった

一方で、「この袖だけ気に入ったから別の服にも使いたい」という要求は確かにあった。
ここで見えてきたのは、project の fork とパーツの再利用は似ているようで別の動機だということだった。

- project の fork は、一着全体の文脈ごと持っていく操作
- library は、気に入った部品だけを資産として抜き出す操作

この役割分担が見えてから、library は「参照し続ける共有部品」ではなく、「コピーして使い、コピー先で自由に直す」モデルに寄った。これは shadcn/ui 的な扱いに近い。

この時点で、Loomit は「project を複製して育てる流れ」と「part を publish して流用する流れ」を分けて考えるようになった。

## version ではなく name + variant に考え直した

次に大きかったのは、パーツの `version` という考え方が服作りに合っていないと気付いたことだった。

ソフトウェアでは、新しい version が古い version より進んでいる、という前提を置きやすい。
しかし洋裁パーツでは、`puff-sleeve-v3` と `puff-sleeve-v5` は優劣のある新旧ではなく、単に違う選択肢であることが多い。

この違いが見えてから、

- `name` と `variant` を分ける
- `variant` を大小比較しない
- 互換判定は version 比較ではなく寸法条件で行う

という方向に設計を修正した。

これは細かいスキーマ調整ではなく、Loomit が何を比較し、何を「新しいもの」と見なさないかを決め直す重要な転換だった。

## prototype notes は project state とは別物だった

試作を繰り返していると、残したいのは現在の寸法や connector 情報だけではなかった。

「この条件では腕が上がりにくかった」「この形だとまだ突っ張る」「この残布なら襟やカフスに再利用できる」といった知見は、服そのものの状態ではなく、作る人の経験だった。

そのため、`prototype-notes` は `loomit.yml` の中に埋め込むより、独立した知識データとして扱う方が自然だった。

また、project を fork して服の実体は分岐しても、試作から得た学びは引き継がれてよい。
ここでも「服の状態」と「作る人の知識」は別だという整理が効いた。

## Git 的に扱いたいのに diff が足りなかった

ここで、設計の中心的な欠落がはっきりした。

project を fork できても、library を持てても、prototype note を残せても、変更を意味のある差分として読めなければ Git 的な作業は成立しない。

当時の Loomit では、変更はまだ ファイル内容（blob）の差分 に近く、
「ダーツ幅を変えた」「ダーツを移動した」といった設計上の変更が、バージョン管理に使える形で見えていなかった。

ここで初めて、「足りなかったのは diff だ」と明確に言えるようになった。

Loomit の中心を validator だけで考えていた時期には、この欠落は見えにくかった。
Git 的な道具として見直したことで、diff の必要性が前景化した。

## diff 可能なドメインにしないとバージョン管理にならない

diff が必要だと分かると、次の問題はもっと根本的だった。

単に `loom diff` というコマンドを生やせば解決するわけではない。比較されるデータ自体が diff 可能な構造になっていなければ、出てくるのは座標やファイルの差分でしかない。

特に大きかったのは、ダーツのような「人がよく触る編集フィーチャ」が schema に十分現れていなかったことだった。

ダーツ幅を 30mm から 35mm に変えたことを、

- 座標の塊の変化として見るのか
- 編集フィーチャのパラメータ変更として見るのか

で、意味のある履歴になるかどうかが大きく変わる。

ここで設計は、「座標を比較する」のではなく、「編集フィーチャを id 付きの構造として持ち上げ、その差分を読む」方向に進んだ。

## `.val` と `part.loom` の役割分担がはっきりした

diff を成立させるために、幾何の正本と Loomit 側の表現の境界も見直された。

Valentina の `.val` は、座標の塊ではなく、点や数式や寸法参照を持つパラメトリックな構築レシピである。
そこには設計変更の粒度を持ち込める余地がある。

一方、Loomit が自前で CAD の write を持ち始めると、責務が急に重くなる。

そのため、

- 幾何の正本は `.val`
- `part.loom` は `.val` から射影した domain representation と Loomit 固有メタ
- Loomit は read と解析と diff を担う
- geometry の focused check は Seamlint
- 実際の補正や CAD write は Truer あるいは外部 CAD 側

という線引きが整理されていった。

この時点で、`loom diff` は Loomit から外すべき機能ではなく、
むしろ Loomit が正本ファイルの意味を読むための中核機能として位置付いた。

## diff は比較表示ではなく design review surface になった

diff を入れるだけなら、単なる比較表示で終わる可能性もあった。

しかし実際には、Loomit が必要としていたのは「この変更案を残すか、捨てるか」を判断するための読み面だった。

そこから、

- decision summary
- prototype note との関連付け
- Seamlint へ渡す re-check hints

のような方向が見えてきた。

つまり `loom diff` は、ファイル差分を見る画面ではなく、設計判断のための surface になっていった。

## まだ途中にあるもの

今の Loomit は、最初の発想だった「洋裁の git」に完全に到達したわけではない。

まだ途中にある課題も多い。

- どの編集フィーチャまで `part.loom` に持ち上げるか
- diff の粒度をどこまで human-readable にするか
- prototype note の関連度をどう絞るか
- Seamlint と Truer の境界をどう保つか

ただ、少なくとも今は、何が不足していて、なぜその不足が問題なのかを以前よりはっきり言えるようになった。

その意味で、この設計史は「完成した正解」の記録ではなく、Loomit が validator から git 的な道具へ考え直され、そのために diff 可能なドメインを必要とした過程の記録である。
